## 1. Цели и границы системы

### 1.1 Цели

Система должна поддерживать одновременно:

1. обычные PBR-материалы (пластик, металл, резина, кожа, стекло);
2. автомобильную краску Basecoat/Clearcoat как отдельный тип поверхности;
3. заводские цвета и пользовательскую смену цвета;
4. paintjob как **самостоятельный графический слой поверх базовой краски** `[Т]`;
5. независимые decals `[Т]`;
6. смешивание текстурных слоёв в albedo-пространстве;
7. сохранение и загрузку состояния автомобиля;
8. совместимость со старыми машинами, текстурами и пользовательскими скинами.

### 1.2 Границы (что этим документом не делается)

- Не добавляются поля в SCX и не меняются его версии `[Ф]`
  (`SCX_MATERIAL_FORMAT.md` §8: формат замораживается после стабилизации
  модели материала).
- Не меняются существующие shader-интерфейсы и uniform-контракты.
- Не создаются бинарные форматы: определяются только требования и границы
  совместимости.
- Не проектируются light system, IBL-prefilter, DFG LUT, SSR: они внешние
  зависимости, перечисленные в §12.4.
- Не реализуется редактор материалов (`AUTOMOTIVE_RENDERING.md`: материал-и-
  редактор — последний этап).
- Не выводятся лимиты «из головы»: всё, что похоже на лимит, помечено как
  бюджет, подлежащий измерению `[П]`.

### 1.3 Установленная основа, на которую опирается проект

| Факт | Источник |
|---|---|
| «Краска» в существующих данных — это **ID текстуры**, без параметров материала | `RENDER_DATA_CONTRACT.md` §15, `[Э12]`, `[Э13]` |
| `Record::state.texture` — ID ресурса (packed или runtime `0xFFFFxxxx`), не RGB | `[Э7 §4.2]`, `[Э14]` |
| Отдельное состояние tint существует независимо от ID текстуры | `[Э4]`, `[Э5 §3]` |
| Перекраска сейчас = подстановка текстуры в **base**-слой группы | `bgfx_lighting.cpp:194-195` |
| Второй текстовый слой материала (`DiffuseMixSecond`, `0x06000001`) уже есть в SCX и уже композитится по alpha | `scx_mesh.cpp:293`, `fs_vehicle.sc:68`, `fs_mesh.sc:180-182` |
| Legacy `duplicate()` делит ресурс, copy-on-write не найден | `[Э13 §5]`, `[Э14 §5]` |
| Pipeline линеен: цветовые карты sRGB, сцена RGBA16F, ACES в present | `LINEAR_MIGRATION.md` ч.3, `RENDERING_ARCHITECTURE.md` |
| GGX-prefilter и DFG LUT **не реализованы**; куб 512/RGBA8 с авто-mip | `LIGHTING_AUDIT.md`, `AUTOMOTIVE_RENDERING.md` Stage 1 |

## 2. Терминология

Термины ниже различаются строго; смешивание запрещено.

| Термин | Определение | Где живёт |
|---|---|---|
| **Material Definition** | описание физических и визуальных свойств поверхности; иммутабельно; адресуется по id | SCX (обычные) или игровая библиотека (краска) `[Ф]` `RENDER_DATA_CONTRACT.md` §2 |
| **Material Slot** | семантическая точка назначения материала в геометрии; объявлена моделью; связывает одну или несколько групп геометрии | SCX |
| **Material Binding** | связь «группа геометрии → слот» или «группа → материал напрямую» | SCX |
| **Material Assignment** | выбор материала для слота на конкретном экземпляре (машине/детали); изменяемое, сохраняемое | состояние экземпляра |
| **Paint Definition** | Material Definition с моделью затенения AutomotivePaint | игровая библиотека |
| **Surface Layer** | графический слой (paintjob, decal), наложенный на базовую поверхность; не является BRDF | данные экземпляра |
| **Layer Stack** | упорядоченный список поверхностных слоёв для конкретного слота экземпляра | данные экземпляра |
| **Resolved Material** | итоговый CPU-набор параметров и ссылок на текстуры для одного draw | формируется Material System |
| **Legacy Paint** | псевдо-определение: ID текстуры + tint, воспроизводящее поведение оригинала | адаптер совместимости |

**Правило:** Material Definition ≠ текстура; Material Slot ≠ texture index;
Material Assignment ≠ Material Definition; Surface Layer ≠ BRDF `[Ф]`
(`SCX_MATERIAL_FORMAT.md` §3).

## 3. Material Definition / Slot / Binding

### 3.1 Material Definition

`[П]` Единое описание, не зависящее от источника:

| Группа полей | Поля | Применимость |
|---|---|---|
| идентификация | `definition_id`, `shading_model`, `source` (диагностика), `provenance` (scx / paint-library / legacy / dev) | все |
| общие карты | `albedo`, `normal`, `ao`, `emissive` | все |
| общие скаляры | `normal_scale`, `basecolor_factor`, `alpha_mode` (opaque / cutout / blend), `opacity` | все |
| PBR | `metallic`, `roughness`, `emissive_strength` | `shading_model = PBR_Generic` |
| automotive | `basecoat{color, metallic, roughness, normal, flake}`, `clearcoat{roughness, reflectance/ior, intensity, normal}`, `finish_type` (gloss/candy/metallic/matte/satin/chrome) | `shading_model = AutomotivePaint` |
| legacy | `legacy_texture_id`, `legacy_tint`, `shininess`, `specular` | `shading_model = LegacyBlinn` |

Требования:

- `shading_model` — единственный переключатель поведения; наличие
  automotive-полей не делает материал краской `[Т]`.
- Поле `provenance` обязательно для диагностики: рендер не должен выяснять
  происхождение материала `[Ф]` (`RENDER_DATA_CONTRACT.md` §6).
- Определение иммутабельно. Всё изменяемое живёт в Assignment / Layer Stack.
  Это прямое следствие legacy-вывода: перекраска не должна уничтожать
  roughness/clearcoat `[Ф]` (`SCX_MATERIAL_FORMAT.md` §3).

### 3.2 Material Slot

`[П]` Слот объявляется моделью и содержит:

| Поле | Смысл |
|---|---|
| `slot_id` | стабильный в пределах модели; не равен texture index |
| `role` | `Ordinary` / `Paint` / `Glass` / `Emissive` / `Trim` (минимальный набор) |
| `geometry_groups[]` | одна или несколько групп геометрии |
| `material_ref` | для model-owned: id определения в SCX |
| `paint_model` | для `role = Paint`: разрешённая модель (например `AutomotivePaint`) |
| `fallback_ref` | материал, если назначение отсутствует |
| `permitted_layers` | какие типы поверхностных слоёв допустимы (paintjob / decals / none) |

Ответы на поставленные вопросы:

1. **Идентификация:** `slot_id` из SCX (см. §10), стабильный, не индекс массива.
2. **Связь с геометрией:** слот ссылается на группы; группа может принадлежать
   только одному слоту (иначе неоднозначность).
3. **Отделение от texture index:** texture index — это адрес текстуры в списке
   текстур модели (`geo.textures`), существующий legacy-механизм `[Ф]`
   (`scx_mesh.cpp:71`, `bgfx_lib_backend.cpp:2532-2533`). Слот — семантика, а не
   адрес текстуры. Внутри model-owned материала texture index остаётся как
   legacy-ссылка; слой `role = Paint` своего texture index не требует.
4. **Несколько независимых слотов:** возможны архитектурно; количество
   определяется контентом, а не константой `[П]`. Обязательного двухцветного
   контента это не обещает `[Ф]` (`RENDER_DATA_CONTRACT.md` §5.3).
5. **Один материал на несколько слотов:** да; определения иммутабельны, поэтому
   совместное использование безопасно. Изменяемое состояние (слои) — у
   Assignment, не у определения.
6. **Совместимость со старой геометрией:** для SCX без слотов синтезируется
   единственный слот `Ordinary` на все группы; для деталей кузова с признаком
   `paint` синтезируется слот `Paint` с `fallback_ref` = Legacy Paint `[П]`
   (§11.2).

**Ограничение, унаследованное из аудита:** поддержка нескольких слотов **не
выводится** из legacy-механизма Painter. Тот механизм обходит несколько
элементов контекста, но их назначение не установлено `[Ф]` (`[Э13 §2]`,
`[Э14 §3–4]`). Количество слотов обосновывается контрактом SCX/материалов, а не
этой аналогией `[Т]`.

### 3.3 Material Binding / Assignment

`[П]` Три уровня, которые нельзя сливать:

```
Material Definition  (что за поверхность)          — иммутабельно, разделяемо
        ▲
Material Binding     (группа → слот)                — в модели (SCX)
        ▲
Material Assignment  (слот → определение, экз.)     — состояние экземпляра
        ▲
ResolvedMaterial     (итог для draw)                — вычисляется на кадр
```

| Уровень | Кто меняет | Сохраняется |
|---|---|---|
| Definition | контент/мод, редактор | да, как контент |
| Binding | автор модели (экспортёр) | да, в SCX |
| Assignment | игровая логика, пользователь | да, в состоянии экземпляра |
| ResolvedMaterial | рендер | нет (кэш кадра) |

`Assignment` содержит: `slot_id`, `definition_id` (или legacy-пару
`texture_id + tint`), `layer_stack_id`. Для слотов `Ordinary` assignment
обычно отсутствует — материал уже фиксирован моделью `[Ф]`
(`RENDER_DATA_CONTRACT.md` §6).

## 4. Generic PBR

`[П]` Классическая metallic-roughness модель (перенос из `PBR_PLAN.md`):

```
F0      = mix(vec3(0.04), baseColor, metallic)
diffuse = baseColor * (1 - metallic)
```

| Свойство | Носитель | Примечание |
|---|---|---|
| Base Color | `albedo` × `basecolor_factor` | sRGB-декод `[Ф]` (`LINEAR_MIGRATION.md` ч.3) |
| Metallic / Roughness | скаляры + опциональная упакованная карта | линейные данные, без sRGB `[Ф]` |
| Normal | карта + `normal_scale` | тангент-базис нужен, сейчас его нет `[Ф]` (`AUTOMOTIVE_RENDERING.md`, Stage 1) |
| AO | карта; либо lightmap как AO-кандидат | lightmaps сейчас не доходят до GPU `[Ф]` (`LIGHTING_AUDIT.md`) |
| Emissive | карта + сила | не источник света `[Ф]` (`RENDER_DATA_CONTRACT.md` §10) |

**Generic PBR не получает** paintjob, decals, clearcoat и flake. Эти компоненты
существуют только у `shading_model = AutomotivePaint` `[Т]`. Проверка — по
`shading_model` в ResolvedMaterial, а не по наличию полей.

## 5. Automotive Paint

### 5.1 Два слоя, одна физика

`[П]` (модель из `PBR_PLAN.md`, здесь уточнена граница ответственности):

| Слой | Что описывает | Собственные параметры | Что наследует |
|---|---|---|---|
| **Basecoat** | пигмент, металлик, перламутр | `base_color`, `metallic`, `roughness`, `normal`, `ao`, `flake_intensity`, `flake_scale` | геометрию, UV, AO подложки |
| **Clearcoat** | прозрачный диэлектрический лак | `roughness`, `reflectance`/`ior`, `intensity`, опциональный `normal` | всё, что под ним, включая графику |
| **Substrate** | материал под краской (грунт/пластик) | обычные PBR-поля | — |

Энергетика: часть света отражается лаком (Fresnel диэлектрика), остаток
проходит в basecoat, рассеивается и возвращается через лак. Это **два лепестка
BRDF**, но **одна** поверхность и **один** проба окружения: отдельные
отражающие поверхности не проектируются `[Т]`.

### 5.2 Типы отделки

`[П]` `finish_type` — предустановка параметров, а не отдельный шейдер:

| Тип | basecoat | clearcoat |
|---|---|---|
| Gloss | низкая roughness | есть, низкая roughness |
| Metallic | flake > 0 | есть |
| Candy | полупрозрачный цветной слой над металликом | есть |
| Matte | высокая roughness | слабый/отсутствует |
| Satin | средняя roughness | слабый |
| Chrome | metallic = 1, высокий reflectance | лака нет |

`finish_type` разворачивается в параметры на этапе загрузки; шейдер видит только
числа (требование «параметры без перекомпиляции шейдеров» `[Ф]`
`AUTOMOTIVE_RENDERING.md`, Project rules п.4).

### 5.3 Чего automotive-краска не делает

- Не является tint: `instance.color` (legacy) остаётся отдельным механизмом и в
  новой модели обслуживает только `shading_model = LegacyBlinn` `[Ф]` (§11.2).
- Не кодируется в ID текстуры: идентификатор назначения — `definition_id` `[Т]`.
- Не заменяет текстуру: смена краски меняет параметры и карты basecoat, а слои
  (paintjob, decals) остаются `[Т]` (инварианты §12).

### 5.4 Совместимость с legacy-цветом

`[П]` Отдельная задача миграции, не часть физической модели:

- legacy-цвет (`CARCOLORS[i]` → `state.texture`) превращается в
  `LegacyPaint { texture_id, tint }`, а не в automotive-краску;
- автоматический подбор `finish_type` по legacy-данным **не делается**: в
  данных нет ни roughness, ни clearcoat `[Ф]` (`RENDER_DATA_CONTRACT.md` §15);
- перевод legacy → AutomotivePaint выполняется как явная операция контента или
  мода, с записью `provenance` `[П]`.

## 6. Paintjob

### 6.1 Требование

`[Т]` Paintjob — **самостоятельный графический слой поверх базовой краски**:

1. детали назначается базовый цвет краски;
2. поверх назначается paintjob;
3. прозрачные области paintjob пропускают базовый цвет;
4. непрозрачные показывают графику;
5. смена базового цвета не уничтожает и не изменяет paintjob;
6. удаление paintjob возвращает чистую базовую краску.

### 6.2 Формат слоя

`[П]`

| Свойство | Значение |
|---|---|
| Данные | RGBA-текстура: RGB — графика, **A — маска прозрачности** (0 = чистая краска) |
| Доп. маска | опционально отдельный канал/текстура (metallic/roughness/normal override) — как расширение, не в первой версии |
| Композитинг | `albedo = mix(paint_albedo, paintjob.rgb, paintjob.a * opacity)` в **линейном** пространстве |
| Цветовое пространство | RGB paintjob — sRGB (декод при сэмплировании), alpha и маски — линейные `[Ф]` (правило `LINEAR_MIGRATION.md`) |
| UV | собственный `channel`, `scale`, `offset` (как существующий `ScxTextureMap`), опционально поворот — §7.3 |
| Фильтрация / мипы | трилинейная, mip-цепочка обязательна (текстура рассматривается в движении и в отражениях); alpha-канал не должен «съедаться» премультипликацией без явного решения |
| Влияние на PBR | по умолчанию только albedo; roughness/metallic paintjob наследует от basecoat |

### 6.3 Наследие оригинального `mix` — что уже есть

`[Ф]` В SCX v4 существует второй текстурный слот материала
`DiffuseMixSecond` = property `0x06000001` со своим `ScxTextureMap`
(`scx_mesh.cpp:293`, `include/slrr/scx_mesh.hpp:31-37`). Композитинг:

```glsl
// fs_vehicle.sc:68
vec3 albedo = mix(base.rgb, detail.rgb, detail.a * u_vehicleLayers.x) * u_vehicleDiffuse.rgb;
// fs_mesh.sc:180-182 — то же для статических мешей
tex.rgb = mix(tex.rgb, layer.rgb, layer.a);
```

Это структурно **тот же примитив**, который нужен paintjob: второй слой с alpha-
маской поверх базовой текстуры, с собственными UV-параметрами. То есть
оригинальная концепция «`paintable` поверх `default_color`» в OpenSLRR уже
частично материализована как `0x06000001`.

**Чего не хватает для полноценного paintjob:**

| Ограничение текущего `mix` | Следствие |
|---|---|
| ровно **один** mix-слой на группу | нельзя стек слоёв (paintjob + decals) |
| нет собственного `opacity`, только alpha текстуры | нет независимой регулировки |
| нет собственного roughness/normal override | графика не может быть глянцевой/матовой отдельно |
| нет независимого сохранения: слой задан моделью (SCX), не состоянием машины | пользовательский paintjob некуда положить |
| UV-преобразование общее `ScxTextureMap` (channel/tiling/scale/offset), без поворота | декалям недостаточно (§7.3) |
| композитинг до освещения, вместе с `u_vehicleDiffuse` | правильно, и это надо сохранить |

`[П]` Поэтому paintjob проектируется как **обобщение** существующего
mechanics: тот же albedo-space alpha-блендинг, но слой — данные экземпляра, а не
поле SCX, и таких слоёв может быть несколько.

**Не путать** alpha-композитинг графики с физическим смешиванием BRDF `[Т]`:
paintjob меняет albedo поверхности, но не создаёт второй лепесток отражения.

## 7. Decals

### 7.1 Требование

`[Т]` Декали независимы от paintjob и от базовой краски: отдельные объекты с
собственным размещением, порядком наложения и временем жизни.

### 7.2 Данные одного decal-слоя

`[П]`

| Поле | Смысл |
|---|---|
| `texture_ref` | ссылка на контент (файл/ресурс), не runtime ID |
| `slot_id` | на какой слот наносится |
| `order` | порядок наложения в стеке |
| `transform` | размещение (§7.3) |
| `opacity` | 0..1 |
| `blend_mode` | normal / multiply / add (ограниченный набор) |
| `alpha_mode` | cutout / blend |
| `roughness_override`, `metallic_override`, `normal_ref` | опционально, если графика отличается по блеску |
| `provenance` | user / legacy / baked |

### 7.3 Размещение

`[П]` Базовая система — аффинное преобразование в UV-пространстве слота
(`scale`, `offset`, `rotation`) плюс `channel` (UV0/1/2). Это расширение
существующего `ScxTextureMap` на поворот.

`[?]` Проекционные декали (планарная проекция по нормали/цилиндру) — отдельный
вопрос: они нужны для нанесения «на лету» в произвольную точку поверхности, но
требуют иного сэмплирования и иной стоимости. В первую версию не входят.

### 7.4 Варианты реализации и их последствия

| Вариант | Плюсы | Минусы | Стоимость |
|---|---|---|---|
| **A. Отдельные runtime-объекты** (N сэмплов в шейдере) | полная независимость редактирования; нет запекания; порядок и параметры меняются в любой момент | N выборок текстур + N альфа-блендов; рост числа variant'ов; хуже батчинг | линейно по N; практично при N ≤ 2–3 `[П]` |
| **B. Композит в отдельную текстуру** (per-instance atlas) | одна выборка в шейдере; дешёвый рендер | нужен GPU-композит при каждом изменении; отдельное владение памятью; сложнее порядок слоёв после композита | разовая стоимость при правке; память на atlas |
| **C. Запекание в paintjob** | минимальная стоимость рендера; простота сохранения | теряется независимое редактирование (нарушает §12.3), если необратимо | нет runtime-стоимости, есть потеря функций |
| **D. Гибрид** (A до лимита, затем явный bake в B) | независимость в обычном случае; предсказуемая стоимость на сложных машинах | два пути, нужен явный API «flatten», нужно хранить исходный стек | средняя |

`[П]` Рекомендация — **D**. Обязательные условия:

- запекание только по явной команде, с сохранением исходного Layer Stack;
- запекание всегда создаёт **свою** изменяемую текстуру (явное клонирование,
  §9) и никогда не пишет в общий ресурс;
- читаемая деградация: при превышении лимита движок не «теряет» декаль молча, а
  сообщает в диагностику, какой слой не применён.

`[Т]` Нельзя сводить все декали к одной заранее подготовленной текстуре, если
это лишает их независимого редактирования: вариант C допустим только как
явное, обратимое действие пользователя.

### 7.5 Сохранение

`[П]` В состоянии экземпляра сохраняется весь стек (порядок, трансформы,
opacity, ссылки на контент, provenance). Запечённый вариант сохраняется вместе с
флагом `baked` и ссылкой на исходный стек, чтобы пользователь мог «распечь
обратно».

## 8. Clearcoat и порядок слоёв

### 8.1 Базовый порядок

`[П]` Исходная гипотеза, проверенная на согласованность:

```
Substrate (материал SCX: albedo/roughness/metallic под краской)
   → Base Paint (basecoat automotive: цвет, metallic, flake, roughness, normal)
      → Paintjob (RGBA, alpha-маска)
         → Decals (0..N, упорядоченные)
            → Clearcoat (один диэлектрический лак на всё)
               → ResolvedMaterial → PBR shader
```

### 8.2 Что каждый слой может менять

| Слой | Base Color | Alpha | Roughness | Normal | Участвует в clearcoat |
|---|---|---|---|---|---|
| Substrate | да (если краски нет) | да (`alpha_mode`) | да | да | нет |
| Base Paint | **да** (задаёт) | нет (краска непрозрачна) | да | да | да (под лаком) |
| Paintjob | да, через alpha-бленд | да (маска) | по флагу override | по флагу override | да (под лаком) |
| Decals | да, через alpha-бленд | да (маска/cutout) | по флагу override | по флагу override | да (под лаком) |
| Clearcoat | нет | нет | **своя** | своя (опц.) | — |

Ключевое: `roughness` и `normal` — **параметры итоговой поверхности**, а не
отдельные отражающие слои. Все override'ы сводятся в один набор параметров
поверхности; второй лепесток BRDF существует только у лака (физическое
обоснование: диэлектрическая плёнка над пигментированной базой) `[Т]`.

### 8.3 Почему лак накрывает всё

`[П]` Лак — реальная плёнка над графикой. Если наносить paintjob «поверх лака»,
то глянец и отражения оказались бы под графикой, что физически неверно и
визуально читается как наклейка. Поэтому порядок фиксирован: графика
композитится в **albedo** (и, по флагам, в roughness/normal), а лак применяется
к результату.

### 8.4 Передача в шейдер

`[П]` `ResolvedMaterial` для automotive содержит: `baseColor`, `metallic`,
`roughness`, `normal`, `ao`, `clearcoat{roughness, reflectance, intensity,
normal}`, `emissive`, список текстурных выборок слоёв и их трансформов.
Больше ничего: шейдер не знает, откуда взялся paintjob.

## 9. Texture Ownership и runtime resources

### 9.1 Что известно из legacy-аудита (основа)

| Факт | Следствие для новой системы |
|---|---|
| `ResourceRef.duplicate()` делит ресурс, пиксели не копирует `[Ф]` `[Э13 §5]` | нельзя полагаться на `duplicate` как на «сделать копию» |
| Copy-on-write в исследованной цепочке **не найден** `[Ф]` `[Э14 §5]` | совместное владение = совместное изменение; нужен явный механизм |
| Painter меняет существующие текстуры, а не создаёт новые `[Ф]` `[Э13]` | «покраска» в новой системе не должна мутировать разделяемый ресурс |
| `0xFFFFxxxx` — runtime-пространство, не постоянный ID `[Ф]` `[Э14 §6]` | runtime ID никогда не попадает в сохранение |
| Связь Painter-context ↔ resource node частично неизвестна `[Ф]` `[Э14 §3–4]` | нельзя опираться на legacy-контекст как на источник истины |

### 9.2 Требования `[П]`

| Требование | Содержание |
|---|---|
| **Immutable source** | текстуры контента (RPK/SCX) только для чтения; ни один слой на них не пишет |
| **Editable per-instance** | всё изменяемое (paintjob, decal atlas, запечённые слои) — отдельные ресурсы, принадлежащие экземпляру |
| **Явное клонирование** | операция «сделать редактируемую копию» — отдельный вызов с явной семантикой; никакого неявного COW |
| **Владение** | у изменяемого ресурса ровно один владелец (Assignment/Layer Stack); ссылки других экземпляров на него запрещены |
| **Refcount** | для иммутабельных ресурсов — разделяемое владение; для изменяемых — единственный владелец и освобождение вместе с экземпляром |
| **Освобождение** | детерминированное: при удалении слоя/экземпляра; без «висящих» ресурсов после flatten |
| **CPU/GPU** | CPU-описание (Layer Stack) — источник истины; GPU-текстура — кэш, пересоздаётся при изменении; синхронизация по номеру версии слоя |
| **Персистентность** | сохраняется **контент и параметры слоёв**, не runtime ID и не GPU-ресурс |
| **Диагностика** | каждый ResolvedMaterial сообщает, какие слои применены, какие отброшены и почему |

### 9.3 Формально: три класса ресурсов

`[П]`

1. **Immutable content texture** — загружается из RPK/файла, разделяется,
   никогда не мутирует. Может адресоваться legacy packed ID (§11).
2. **Instance editable texture** — результат явного клонирования/запекания;
   один владелец; переживает перезагрузку только через сохранение содержимого.
3. **Transient render target** — промежуточный композит, живёт в пределах кадра
   или до изменения слоя, не сохраняется.

### 9.4 Запрет, унаследованный из legacy

`[Т]`/`[Ф]` Изменение текстуры одной детали не должно непреднамеренно менять
другую. Поскольку legacy-механизм именно это и позволял (`duplicate` + мутация),
новая система обязана:

- не выдавать редактируемый ресурс двум экземплярам;
- при попытке «назначить тот же paintjob двум машинам» разделять *описание*, а
  не пиксели;
- иметь диагностический тест: правка слоя у экземпляра A не меняет экземпляр B.

## 10. SCX и размещение данных

### 10.1 Что уже принадлежит SCX `[Ф]`

- геометрия, группы, индексы, UV-каналы, vertex colors;
- материал группы: `diffuse RGBA`, `specular RGB`, `shininess`,
  `material_type`, `reflection_strength`, `alpha_reference`, `material_flags`,
  texture index + `ScxTextureMap` (`scx_mesh.hpp:24-45`);
- legacy-слоты текстур: `texture_index`, `mix_index`
  (`0x06000001`), `reflection_index`, `lightmap_index`, `illumination_index`;
- имя материала (v4 `0x08000000`) `[Ф]` (`scx_mesh.cpp:305-311`).

### 10.2 Сравнение вариантов размещения

| Вариант | Плюсы | Минусы | Последствия для старых SCX |
|---|---|---|---|
| **A. Расширять SCX** | всё в одном файле; экспортёр уже рядом; round-trip естественен | формат замораживается раньше времени; правки материалов требуют пересохранения модели; библиотека краски в SCX противоречит §2 | старые читаются, если строго версионно и без переупорядочивания |
| **B. Sidecar-ресурсы материалов** | быстрый старт, ничего не ломает; удобно для BRDF-разработки | риск «второго источника истины» `[Ф]` (`SCX_MATERIAL_FORMAT.md` §2); моды расползаются по файлам | нет изменений |
| **C. Отдельные игровые ресурсы (resource system)** | правильное место для библиотеки краски и слоёв; адресация по id; не трогает геометрию | нужен новый тип ресурса и загрузчик; сложнее экспорт из редактора | нет изменений |
| **D. Смешанная модель** | у каждого типа данных своё место | требует дисциплины и явного контракта | нет изменений |

### 10.3 Рекомендация `[П]`

**D — смешанная модель**, с жёстким разделением:

| Данные | Место |
|---|---|
| геометрия, группы, Binding (группа → слот), model-owned материалы, `slot_id`, `role`, `fallback_ref` | **SCX** (расширение версионным блоком, позже) |
| библиотека Paint Definition (иммутабельные) | **игровой ресурс** (не SCX, не `CARCOLORS`) |
| Material Assignment (какой paint выбран) | **состояние экземпляра** |
| Layer Stack (paintjob, decals) | **данные экземпляра** (отдельно от геометрии) |
| Legacy Paint / legacy texturе-ID | адаптер, читающий существующие данные |

Обоснование: это ровно разделение ответственности из
`RENDER_DATA_CONTRACT.md` §1, плюс явное место для слоёв, которых там ещё не
было.

**Что требует согласования:** `[?]`

1. Нужен ли `slot_id` в SCX в первой версии (сейчас групповая адресация уже
   есть; слот можно ввести как «группа + роль» без изменения формата).
2. Хранить ли `role = Paint` как дополнительный признак группы или как
   отдельный блок.
3. Допустимо ли, чтобы один слот ссылался на несколько групп в разных
   подобъектах, или это должна быть одна группа.
4. Где живёт библиотека краски: новый тип ресурса против расширения
   существующей структуры (открытый вопрос `RENDER_DATA_CONTRACT.md` §13.1).

## 11. Save/Load и legacy compatibility

### 11.1 Что сохраняется независимо

`[П]`

| Данные | Форма | Ссылки |
|---|---|---|
| Material Assignment | `slot_id → definition_id` (+ параметры override) | по id контента |
| Base Paint выбор | часть Assignment | по `definition_id` |
| Paintjob | слой: текстура-контент + трансформ + opacity + provenance | по ссылке на контент |
| Decals | упорядоченный список слоёв | по ссылкам на контент |
| Пользовательские текстуры | содержимое + логическое имя | содержимое, не runtime ID |
| Generic PBR overrides | по `definition_id` или по `slot_id` | по id |

Инвариант: **runtime ID не сохраняется как идентификатор содержимого** `[Т]`
(прямое следствие `[Э14 §6]`).

### 11.2 Legacy: что обязано читаться

| Legacy-механизм | Что читаем | Как представляем |
|---|---|---|
| `Record::state.texture` (packed) `[Ф]` | ID ресурса | `LegacyPaint { texture_id }` → assignment слота `Paint` |
| `PartRender::colors` / `instance.color` `[Ф]` | tint `0xffffff` по умолчанию | `LegacyPaint.tint` |
| `Part.save/load` (ResourceRef) `[Ф]` | сохранения машин | читается существующим путём без изменений |
| Skin Preset (SDAT тип 2, пары «тип детали → ordinal») `[Ф]` `[Э9]` | манифест | импорт в Layer Stack с `provenance = legacy` |
| JPEG sidecar `<манифест>.<ordinal>` `[Ф]` `[Э9]`, `[Э10]` | изображение paintjob | paintjob-слой, привязанный к детали/слоту |
| `DiffuseMixSecond` в SCX `[Ф]` | второй слой материала модели | paintjob-слой с `provenance = content` |

`[П]` Legacy-слой не «улучшается» молча: он остаётся `LegacyBlinn`-поверхностью
до явного перевода. Это защищает от изменения внешнего вида старых машин без
согласия пользователя.

### 11.3 Миграция скинов

`[П]` Порядок импорта legacy-скина:

1. прочитать манифест (пары «тип детали → ordinal»);
2. для каждой пары найти деталь экземпляра и её слот `Paint`;
3. sidecar-изображение положить как paintjob-слой этого слота;
4. сохранить `provenance = legacy`, исходное имя файла и ordinal;
5. исходные файлы не изменять и не удалять.

`[?]` Манифест адресует **типы деталей**, а не слоты. Для моделей с несколькими
paint-слотами соответствие «тип детали → слот» нужно определить; для одной
машины с одним Paint-слотом это тривиально.

### 11.4 Новый формат

`[П]` Требования (без проектирования бинарного формата):

- версионирование и терпимость к неизвестным/отсутствующим полям;
- чтение старых данных без конвертации «на месте»;
- ссылки на контент по логическим id/путям, не по runtime ID;
- сохранение provenance и возможности обратной операции (unbake/unflatten);
- отсутствие обязательства повторять legacy-структуру «manifest + sidecar» для
  новых данных `[Т]`, но обязательная способность **читать** её.

## 12. Rendering и performance

### 12.1 Текущее состояние (факты, на которые опирается бюджет)

| Параметр | Сейчас |
|---|---|
| Текстурные выборки в vehicle-шейдере | base, mix, env (сфера/куб), bake, куб сцены `[Ф]` (`fs_vehicle.sc:15-30`) |
| Формулы отражения | пять несвязанных ветвей по `u_vehicleLayers.w` `[Ф]` (`AUTOMOTIVE_RENDERING.md`) |
| Куб отражений | 512 на грань, RGBA8, авто-mip (не GGX) `[Ф]` |
| Prefilter / DFG LUT | **нет** `[Ф]` |
| Сцена | RGBA16F + ACES, MSAA `[Ф]` |

### 12.2 Бюджет (предложение, требует измерения) `[П]`

| Материал | Выборок | Комментарий |
|---|---|---|
| Generic PBR | 4–5 | albedo, normal, упакованные metallic/roughness, AO, emissive (опц.) |
| Automotive Paint без слоёв | 4 | basecoat albedo, normal, MR, clearcoat normal (опц., иначе переиспользуется) |
| + paintjob | +1 | RGBA-слой |
| + decals | +N, N ≤ 2 в первой версии | далее — явный bake (§7.4) |

Целевой потолок на один автомобильный draw: **6–8 выборок**. Числа — гипотеза,
подлежащая замеру, а не лимит `[П]`.

### 12.3 Шейдеры и варианты

`[П]`

- Один шейдер поверхности с ветвлением по `shading_model` (ветка выбирается
  uniform'ом), а не отдельные программы на каждый тип: это уже принятый подход
  `PBR_PLAN.md` («PBR-ветка по uniform, legacy-путь сохраняется»).
- Число вариантов ограничивается **флагами**, а не комбинаторикой слоёв:
  `model(2) × has_paintjob(1) × decal_mode(2) × alpha_mode(2)` → целевой потолок
  порядка 12; при превышении — свернуть флаги (например, decals через atlas).
- Batching: ключ сортировки — `(program, definition_id, layer_stack_id)`; слой
  не должен ломать батчи, если он общий для нескольких групп.
- Изменение слоя не пересоздаёт программу, только обновляет текстуры/параметры.

### 12.4 Внешние зависимости (не входят в эту систему)

| Зависимость | Почему критична для краски |
|---|---|
| GGX-prefilter куба | без него roughness лака = выбор mip, а не свертка `[Ф]` |
| DFG LUT | без него энергетика спекуляра приблизительна `[Ф]` |
| HDR-куб (RGBA16F) | LDR клиппит отражения, лак не читается `[Ф]` |
| Присутствие света в capture | иначе отражения и освещение расходятся `[Ф]` (`LIGHTING_AUDIT.md`) |
| Тангенс-базис | нужен для normal-карт всех слоёв `[Ф]` |

`[П]` Порядок: краска проектируется так, чтобы **не требовать** prefilter для
корректности albedo-композитинга; качество лака улучшается, когда prefilter
появится. Обратное (проектировать в расчёте на несуществующий prefilter) —
запрещено `[Ф]` (`LIGHTING_AUDIT.md`: «Not implemented: the GGX prefilter»).

### 12.5 Предварительный композит против runtime

`[П]` Сравнение для paintjob/decals:

| Подход | Стоимость кадра | Стоимость изменения | Когда выбирать |
|---|---|---|---|
| Runtime-композит в шейдере | N выборок + N блендов | ~0 | обычный случай, N ≤ 2–3 |
| Предварительный композит в текстуру | 1 выборка | полный проход композита + память | много слоёв, статичный paintjob |
| Гибрид | 1 выборка после bake | композит по команде | сложные машины (рекомендуется) |

## 13. Основные схемы

### 13.1 От SCX до ResolvedMaterial

```
[SCX] геометрия + группы + material block
   │ группа → слот (Binding)                                   [Ф] группы есть; слот — новое [П]
   ▼
[MaterialSlot{slot_id, role, fallback}]
   │ role = Ordinary → MaterialDefinition (SCX)
   │ role = Paint    → Assignment экземпляра → PaintDefinition    [П]
   ▼
[Layer Stack экземпляра] paintjob + decals (для role = Paint)      [П]
   │
   ▼
Material System: сборка параметров
   substrate → basecoat → paintjob → decals → clearcoat          [П]
   │
   ▼
ResolvedMaterial { params, textures[], transforms[], provenance } [Ф-контракт: RENDER_DATA_CONTRACT §6]
   │
   ▼
bgfx backend: bind + draw  (Material System не знает про bgfx)    [Ф]
```

### 13.2 От действия пользователя до сохранённого состояния

```
пользователь меняет цвет / наносит paintjob / ставит decal
   ▼
Assignment / Layer Stack  (единственный владелец изменяемых данных)   [П]
   ├─ изменяемый ресурс: явное клонирование, затем правка             [П] §9
   ├─ версия слоя ++ → GPU-кэш инвалидируется                         [П]
   ▼
сохранение: definition_id + слои (контент-ссылки, трансформы, provenance)
   ├─ runtime ID не пишется                                           [Т]
   ├─ legacy-файлы не изменяются                                      [Т]
   ▼
загрузка: Assignment + Layer Stack → Material System → ResolvedMaterial
```

### 13.3 Границы общего и automotive-specific

| Концепция | Общая для всех материалов | Только automotive |
|---|---|---|
| Material Definition / Slot / Binding | ✔ | — |
| Base Color / Normal / AO / Alpha | ✔ | — |
| Metallic / Roughness (generic MR) | ✔ | — |
| Clearcoat | — | ✔ |
| Basecoat + flake/pearl | — | ✔ |
| Paintjob | — | ✔ (по `permitted_layers`) |
| Decals | — | ✔ |
| Texture ownership / clone / refcount | ✔ | — |
| Save/Load инфраструктура | ✔ | — |

## 14. Архитектурные решения и альтернативы

| Решение | Альтернативы | Почему выбрано | Компромисс |
|---|---|---|---|
| Один `ResolvedMaterial` для всех источников | отдельные пути рендера для SCX/краски/legacy | рендер не должен знать происхождение `[Ф]` | адаптеры на входе |
| Paintjob — данные экземпляра, не поле SCX | paintjob как `DiffuseMixSecond` в модели | пользовательский paintjob меняется без пересборки модели `[Т]` | нужен Layer Stack и его сохранение |
| Композитинг графики в albedo до лака | «графика поверх лака» | физическая корректность `[П]` §8.3 | нельзя сделать «плёнку» отдельным материалом |
| Один лак на итоговую поверхность | лак per-layer | нет физического обоснования нескольких отражающих слоёв `[Т]` | лак нельзя сделать разным на разных decal'ах |
| Явное клонирование вместо COW | COW по refcount | COW в legacy не найден, неявность опасна `[Ф]` `[Э14 §5]` | дороже по памяти при частых правках |
| Legacy — отдельная модель `LegacyBlinn` | конвертация всего в PBR сразу | старые машины выглядят как раньше `[Т]` §11.2 | дублирование пути затенения |
| SCX = геометрия + слоты + обычные материалы | всё в SCX / всё в sidecar | библиотека краски не должна жить в геометрии `[Ф]` | нужен новый тип ресурса |

**Отвергнуто с обоснованием:**

- *«Краска = tint»* — в данных нет параметров, tint не даёт лака `[Ф]`
  (`RENDER_DATA_CONTRACT.md` §15).
- *«Paintjob = замена текстуры»* — нарушает инвариант «смена краски не удаляет
  paintjob» `[Т]`.
- *«Decals всегда в один atlas»* — нарушает независимое редактирование `[Т]`.
- *«Несколько paint-слотов, потому что legacy Painter обходил несколько
  элементов»* — назначение элементов не установлено `[Ф]` `[Э13 §2]`.
