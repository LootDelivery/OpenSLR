# Модель автомобиля, извлечённая из `StreetLegal_Redline.exe`

Документ фиксирует, что именно удалось достать из **оригинального бинарника и его
скриптов** для машины целиком: двигатель, наддув, КПП, сцепление, привод, шины,
подвеска, тормоза, аэродинамика, износ и расходники. Каждое утверждение помечено
уровнем достоверности:

- **[КОД]** — прочитано в декомпилированном коде exe (Ghidra, 4393 функции),
  указан адрес функции;
- **[СКРИПТ]** — прочитано в декомпилированном TUFA-классе игры (`.class` → `.java`);
- **[ВЫВОД]** — следствие из кода, но без прогона; требует проверки;
- **[ОТКРЫТО]** — пока не восстановлено, см. §11.

Артефакты и инструменты, которыми это получено, — в §12.

## 1. Два слоя и цикл обновления

Игра состоит из двух исполняемых слоёв, и физика делится между ними.

| Слой | Что там | Где |
|---|---|---|
| Скрипты (TUFA) | параметры деталей, компоновка, тюнинг, передача констант в `Chassis` | `parts/**/*.class`, `cars/**/*.class` — 1576 классов |
| Native (x86) | вся симуляция: двигатель, трансмиссия, шины, подвеска, износ | `StreetLegal_Redline.exe`, .text 1.99 МБ |

Скрипт не считает физику. Он заполняет объект `java.game.parts.bodypart.Chassis`
(и объекты деталей), а native читает эти поля **по имени** и раскладывает в
собственные структуры.

Ключевые native-функции конвейера:

| Адрес | Роль |
|---|---|
| `0x00416B00` | регистратор native-методов: `(class, name, signature, fn*)` |
| `0x0043E3E0` | конструктор-копировщик объекта физики автомобиля (0xC1C байт) |
| `0x004421xx` | `Chassis.*` natives (23 шт.), включая `getTorque`/`setTorque` |
| `0x00448430` | **загрузка параметров автомобиля**: `Chassis` → структура физики |
| `0x00454500` | **главный шаг физики автомобиля** `step(car, dt)` |
| `0x0046B530` | регистрация natives `DynoData` / `Part` |
| `0x004B77F0` | **дино-свип**: перебор RPM и построение таблиц момента |
| `0x004B6BF0`, `0x004B7020`, `0x004B7740` | физическая модель цикла (термодинамика) |
| `0x0043BE70` / `0x0043BEE0` | интерполяция таблиц момента `torque(RPM)` / `torque2(RPM)` |
| `0x0043C520` | запись значений из деталей в состояние автомобиля (каналы 5…10) |

Порядок: деталь установлена → `fillDynoData`/`updatevariables` (скрипт) → native
собирает таблицы момента → `0x00448430` переносит всё в структуру физики →
`0x00454500` считает шаг.

Размер структуры физики — **0xC1C** байт; размер записи колеса — **0x2B4** байт;
жёсткое тело колеса индексируется страйдом **0xD4**.

### 3.2 Геометрия и производные величины — `0x004B69A0` **[КОД]**

```
bore_2      = bore                       (радиус = bore/2, передаётся как *0.5)
radius      = bore_2                     (диаметр цилиндра)
area        = π · bore_2²
displacement= area · (2·bore_2)          (0x19)
crank_len   = 2 · bore_2
V_total     = area · stroke + Vmin       (0x1c)
compression = V_total / Vmin             (0x1d)
rpm_limit   = (45.0 / bore_2) · 9.549296 (0x23)
```

и `0x004B6A80`:

```
P_boost_ratio  = P_boost / (1 + P_boost)   (0x14c)
P_boost_frac   = 1 / (1 + P_boost)         (0x150)
P_manifold     = P_x · 9.869233e-06 · T    (0x7c, 0x80)   // атм → МПа
```

### 3.3 Дино-свип — `0x004B77F0` **[КОД]**

Для каждой точки `rpm = step, 2·step, … < limit`:

1. `0x004B6BF0` — пересчёт состояния (наполнение цилиндра, фазы, зажигание).
2. `0x004B68C0` + `0x004B7740` — один рабочий цикл; затем **до 10 итераций**
   до сходимости: `|M_prev / M_new − 1| < 0.05`, с релаксацией
   `M = 0.6·M_new + 0.4·M_prev`.
3. Запись `torque[rpm]` (поле `0x62`) и `HP[rpm]` (поле `0x65`) в таблицы.
4. По ходу копятся `maxTorque`, `RPM_maxTorque`, `maxHP`, `RPM_maxHP`.

То есть момент — не формула, а **результат установившегося цикла**, посчитанного
физически. Функция `FUN_004B77F0` вызывается только из `0x0046AA20`
(`DynoData.calcDyno`) — **в рантайме термодинамика не считается**; в игре работают
только готовые таблицы.

`0x004B7740` дополнительно считает:
`BSFC = (fuel/air) / (0.6·bore)`, `fuel_flow = (torque·3600/rpm)·2.2`,
нормировку расхода на цикл.

### 3.4 Что видит физика — интерполяция таблиц **[КОД]**

`0x0043BE70(rpm, physics)` — таблица №1, `0x0043BEE0` — таблица №2 (наддув/закись).
Обе — **кусочно-линейная интерполяция** по точкам `{rpm, M}`:

```
M(rpm) = M[i-1] + (rpm − rpm[i-1]) · (M[i] − M[i-1]) / (rpm[i] − rpm[i-1])
```

Важное следствие: **ниже первой и выше последней точки таблицы момент = 0**
(функция возвращает 0), а не «продолжение кривой».

### 3.5 Рантайм-модель двигателя — `0x00454500` **[КОД]**

Порядок внутри шага (проверено чтением кода):

```
rpm_rad   = car.rpm · 9.549296⁻¹…            (об/мин → рад/с)
throttle  = clamp(|car.throttle|, 0, 1)

// потери
если rpm_rad > 0:  M_fric = −(rpm/(0.05·maxRPM))·(0.05·maxRPM)²·friction_fwd
иначе:             M_fric = +rpm²·friction_rev
оба варианта дополнительно ограничены членом −0.5·rpm·engine_inertia (берётся минимум)

// полезный момент
M = torque_table_1(rpm_rad) · car[0x1DD0]         // 0x1DD0 = износ × множитель

// стартер
если |throttle| ≤ 0.1 и rpm < 0.95·idle_rpm:  M += starter_torque; starter = 1

// закись
если nitro_amount > 0.1 и nitro_tank > 0 и consumption_nitro > 0:
    M += (torque_table_2(rpm)·car.mult_nitro − M) · nitro_amount · limiter
    nitro_tank −= rpm·0.0002·nitro_amount·limiter·dt·consumption_nitro

// отсечка (по темпу, не по «жёсткому» порогу); код 0x004547xx
rate = (rpm − rpm_prev) + rpm
frac = 1.0
eсли rate ≤ limit:
    если rpm > limit:  frac = (limit − rate) / (rpm − rate)
иначе (rate > limit):
    если rpm > limit:  frac = 0.0
    иначе:             frac = (limit − rpm) / (rate − rpm)
M *= frac
rpm_prev = rpm
```
То есть отсечка режет момент **пропорционально приближению к лимиту за шаг**, а не
обнуляет его по достижении порога.

Затем `car.torque_at_clutch = 2 · M · throttle` (`0x1E28`) и момент уходит в колёса
через передаточное число (см. §4).

**Износ двигателя** (`car+0x1E38`) растёт при перекруте:
`f = (|rpm| / maxRPM)⁹`, `w += f·(1 + (0.01·|rpm−90|)²)·dt/τ·friction·100`.
Влияние: множитель `1 − w²·0.6`, при `w ≥ 1` → `0.1` и дополнительно `×0.5`,
а трение `friction_fwd/rev × 50` — то есть перекрученный двигатель резко теряет
мощность и начинает тормозить.

### 3.6 Опоры двигателя **[КОД]**

Двигатель колеблется на опорах как одномассовая система:
```
mass      = engine_mass · 8000
k         = physics[0xA48] / mass           // при малом ходе
k_динам   = ((ωё²+|v|²)·[0xA50] + [0xA4C])·wearfactor + [0xA48]) / mass
x'' = (M·throttle·1000)/mass − |dx|·[0x1E64]·dx·dt
```
Износ опор (`0x1E48`) накапливается, когда ход > 100.

### 3.8 `ClutchF` — мёртвый параметр (важный факт)

`ClutchF` (`Chassis.ClutchF = 500.0`, у деталей `Clutch.maxF = 500.0`) читается в
`0x00448430` и кладётся в `physics+0xC8`. В главном шаге физики (`0x00454500`)
**обращения к `+0xC8` нет ни одного** — проверено поиском по всему корпусу
декомпиляции. Сцепление моделируется не силой, а множителем
`engage = 1 − clutch` (поле `car+0x1DBC`), который масштабирует момент, идущий в
колёса.

Практический вывод для OpenSLRR: ограничение момента «по `ClutchF`» — не
оригинальное поведение; оригинал ограничивает сцепление только входным
значением `clutch` (0…1), которое приходит из скриптов/ввода.

## 4. КПП, сцепление, привод, дифференциал

Скрипты (`Transmission`) **[СКРИПТ]** пишут в `Chassis`:
`gears`, `ratio[8]` (индексы 1…6 — вперёд, `[7]` — задний, отрицательное число),
`rearend_ratio` (`end_ratio`), `starter_torque`, `diff_lock`, `drive_type`
(`DT_FWD=1`, `DT_RWD=2`), `drive_front` (доля момента на переднюю ось);
`fillDynoData` раскладывает привод по колёсам через `WheelRef.setDrive(...)`:
передние получают `drive_front`, задние `1 − drive_front`.

Native-шаг **[КОД]** — полная модель привода `0x00456xxx`:

```
total_ratio = rearend_ratio · ratio[gear]

// 1. приведённые инерции и коэффициент связи
J_engine  = engine_inertia                        // physics[0xE0]
J_drive   = driveline_inertia                     // physics[0xE4]
inv_d     = 1 / (total_ratio² / J_drive)           // = J_drive / total_ratio²
k         = inv_d / (K·J_engine + inv_d)           // K = DAT_0060E028 = 4.0

// 2. две инерции сводятся к одной скорости
rpm_free = rpm_engine + M_engine / engine_inertia   // как если бы сцепление было выжато
shaft    = wheel_shaft · total_ratio                 // скорость со стороны колёс
delta    = (shaft − rpm_free) · k
engage   = 1 − clutch                                // ← вот оно, сцепление

shaft' = (rpm_free + delta − shaft) · engage · 0.999 + shaft
rpm'   = rpm_free + delta · engage · 0.999

car.engine_rpm    = rpm'
car.wheel_shaft   = shaft' / total_ratio
clutch_torque     = (engage · delta / k²) · 10        // → car+0x1E24
```

Это **классическая двухинерционная связь**: за шаг каждая сторона сдвигается к
общей скорости в пропорции своих инерций, а `engage = 1 − clutch` масштабирует,
насколько сильно связь вообще включается. Момент сцепления (`car+0x1E24`) затем
раздаётся по колёсам:

```
для каждого колеса:
    force = (Δshaft / Σ|drive|) · wheel.drive / wheel.radius
    wheel.ang_vel += force ;  wheel.force += force · wheel.radius
```

Связь колёс одной оси (дифференциал) решается отдельным проходом: для пар колёс
считается расхождение угловых скоростей и подтягивается с силой
`dt·50·|Δω|·0.1·diff_lock` (не более 1.0) — то есть `diff_lock` работает как
коэффициент сцепления полуосей, 0…1.

Нейтраль: `gear = 0` → `ratio[0] = 0` → привод не связывается с двигателем,
двигатель крутится свободно (ветка `uVar9 & 0x4000` в шаге).
Задний ход — отрицательное число в `ratio[7]`.

### 4.1 Переключение передач — **это native**, не скрипт **[КОД]**

Исправление предыдущей версии этого документа. Автомат КПП живёт в exe и
состоит из трёх функций; `car.gear` (`0x1DF8`) пишут **только** они:

| Функция | Роль |
|---|---|
| `0x0044D720(physics, car)` | главный контроллер: нейтраль/первая/задняя, вызов расписания |
| `0x0044D4F0(physics, car, rpm_rad, M_now, shaft_rpm)` | **апшифт** |
| `0x0044D620(physics, car, rpm_rad, M_now)` | **дауншифт** |
| `0x0044D410` | средний `wheel+0x11C` по ведущим колёсам; `|v| ≥ 0.2` блокирует переключение |

Вход контроллера — **разница педалей**: `fVar4 = throttle(0x1DB4) − brake(0x1DB8)`.

```
Апшифт (0x44D4F0):
  условия: car[0x1E0C] ≤ 0                      // нет незавершённого переключения
           и (|ratio| ≤ 0.01 или |rpm_двиг − rpm_вал| ≤ 0.1·rpm_двиг)  // сцепление сомкнуто
           и gear < gears
  next_ratio = physics[0x24 + gear*4]            // ratio[gear+1]
  rpm_next   = (rpm / ratio_now) * next_ratio
  M_next     = (rpm_next < RPM_limit) ? table1(rpm_next) : 0
  порог      = 0.95 · min(RPM_limit, maxRPM)
  переключить если:  rpm > порог
                ИЛИ  M_now·ratio_now < M_next·next_ratio     // момент на колесе больше
  → gear += 1;  car[0x1E04] = now + 0.3 c;  событие/звук (0x44D040)

Дауншифт (0x44D620):
  условия: car[0x1E10] ≤ 0  и  gear > 1
  prev_ratio = physics[0x1C + gear*4]            // ratio[gear-1]
  rpm_prev   = (rpm / ratio_now) * prev_ratio
  переключить если:  rpm_prev < порог
                И  M_now·ratio_now·1.15 < M_prev·prev_ratio   // гистерезис 15%
  → gear -= 1;  car[0x1E04] = now + 0.2 c
```

Главный контроллер (`0x44D720`) дополнительно:

- обороты холостого хода `idle` — из `physics+0xEC` (рад/с);
- **первая передача** включается при `throttle − brake > 0.1` и `rpm > 3·idle`;
- **нейтраль** — когда `|wheel_shaft| ≤ 1` и `rpm < 1.2·idle`, и когда газ/тормоз отпущены;
- **задний ход** — при `throttle − brake < −0.1` (то есть по **тормозу**), затем
  `0x1DB4` и `0x1DB8` меняются местами, чтобы тормоз стал «газом» —
  это и есть аркадный реверс SLRR;
- `car[0x1E00]`, `[0x1E04]`, `[0x1E0C]`, `[0x1E10]` — таймеры/флаги блокировки.

### 4.2 Сцепление: **автоматическое**, педали нет **[КОД]**

`car+0x1DBC` пишут только native-ассистенты; в скриптах записи нет:

| Функция | Что делает |
|---|---|
| `0x0044DD70(physics, car, dt)` | старт/защита от заглохания: задаёт целевую точку проскальзывания |
| `0x0044E120(physics, car)` | антипробуксовка: приподнимает сцепление и режет газ |
| `0x0044D330`, `0x00447830` | аварийно ставят `clutch = 1.0` (выжато) |

Алгоритм `0x0044DD70` (выходы: нет газа, нет передачи, `|ratio| < 0.01`):

```
idle = physics[0xEC]                                        // рад/с
цель = (physics[0x10]·0.10471976 − idle)
       · (|ratio/ratio[1]| · throttle · 0.7 + 0.3) · 0.8 + idle
                                                     // физика[0x24] = ratio[1]
```
То есть целевые обороты — от `0.8·(idle + 0.3·(limit−idle))` без газа до
`0.8·(idle + (limit−idle))` при полном газе, масштабированные отношением
текущей передачи к первой.

Скорость изменения — с ограничением (константы из бинарника):
`rate = dt · 33.333336` (τ ≈ 30 мс) при движении к меньшему значению и
`rate = dt · 200` (τ ≈ 5 мс) при движении к большему; затем `rate ≤ 1`.
Порог низкой скорости: `|ω_вал · ratio · rearend| ≤ 0.02·2π · min(RPM_limit, maxRPM)`
(`0.12566371`).

### 4.3 Интегрирование — на шаг, а не на секунду **[КОД]**

В блоке двигателя и связи с приводом **`dt` не участвует**:
`rpm += M / engine_inertia` и `shaft' = …·engage·0.999 + shaft` выполняются
один раз за вызов `0x00454500`. `dt` явно входит только в:
релаксацию/трение шины, диффенциал (`dt·50`), тормоза (`dt·50`), износ,
расход закиси и опоры двигателя. То есть «инерции» в этих местах фактически
уже умножены на шаг интегрирования.

Износ в этой же ветке **[КОД]**:

```
car[0x1E24] = ((engage · delta) / k²) · 10          // мера проскальзывания, НЕ момент
износ сцепления (0x1E40) += |delta · engage · 0.1| · mul
износ КПП      (0x1E50) += (|car[0x1E24]| · 0.01)⁴ · dt · 1e-4 · mul
```

`car+0x1E24` читается **только** в формуле износа КПП (`0x454500`, строка 711)
и нигде не используется как момент. `Transmission.capacity` в native-коде не
участвует.

### 5.2 Что получает native — `WheelRef` **[КОД]**

`setFriction`, `setStiffness`, `setMaxLoad`, `setLoadSmooth`, `setRadius`,
`setWidth`, `setRollRes`, `setBearing`, `setSliction`, `setFrictn_x`,
`setCPatch`, `setPacejka(i, v)` — 17 коэффициентов магической формулы (Pacejka)
в массиве `wheel[0x1E8 + i·4]`, `i = 0…16`.

`Tyre.java` заполняет их так: `[1]=0, [3]=0, [5]=0, [6]=0, [7]=0, [8]=−1,
[9]=0, [10]=0, [12]=1`; `[2]` = `insider_friction` (через `setFriction`).

Износ шины — `wheel[0x15C]`, 0…1. Он напрямую уменьшает оба продольных/поперечных
коэффициента и скорость реакции:
```
f = 1 − wear²·0.4   (при wear ≥ 1 → 0.5)
wheel[0x70] = f · wheel[0x68];  wheel[0x6C] = f · wheel[0x64]
```
При `wear = 1` — **разрыв шины**: радиус `×0.8`, частицы, звук
(`FUN_00491F80`, `FUN_0048CFB0`), повреждение диска (`wheel[0x16C]`).

Отдельно `car+0x1E38` (износ двигателя) и `car+0x1E48` дают тот же множитель
`1 − w²·0.6` — то есть один и тот же закон деградации применён к двигателю и
опорам. **Поправка (2026-11-24):** пара `0x70`/`0x6C` в прикладные силы и шаг
колеса не входит — `0x6C` уходит в `0x1F0` → grip-слот `0x158` (см. выше),
`0x70` в `0x00454500` вообще не читается. Износ влияет на силы только через
разрыв (радиус ×0.8 при 0x15C=1). Тот же множитель трения поверхности
(`поверхность[0x50]`) масштабирует контактный импульс, питающий износ
(строка `fVar2 *= *(susp+0x94+0x50)`): на другом покрытии шина изнашивается
иначе — вот физически значимый эффект слоя поверхностей, а не множитель сцепления.

### 5.3 Модель силы в пятне контакта — `0x0043BA80`, `0x0043BB30`, `0x0043BBD0` **[КОД]**

Сила шины — не таблица и не чистый Pacejka, а **двойной atan-вариант Magic
Formula** с экспоненциальным спадом по нагрузке. Для колеса с коэффициентами
`C0…C10` и скольжением `s`:

```
m      = s·C1 + C2                       // база коэффициента трения
C0m    = m · C0                         // C0 — форма кривой
_e      = exp(−s·C5)
num    = (s·C3 + C4) · _e
arg    = (s·C9 + C10 + slip_angle) · (num / C0m)
t1     = atan(arg)
t2     = atan((s·C7 + s²·C6 + C8) · (t1 − arg) + t1)
F      = m · s · sin(C0 · t2)
F      = max(F, 0)
```

`C0…C10` — первые 11 слотов из 17 (`setPacejka`), массив — `wheel+0x1E8`.
Скрипт `Tyre.java` заполняет только часть (`[1]=0,[3]=0,[5]=0,[6]=0,[7]=0,
[8]=−1,[9]=0,[10]=0,[12]=1`), а `[2]` — через `setFriction`, то есть **основной
коэффициент трения приходит из компаунда** (§5.1), а не из таблицы.

Сглаживание скольжения — `0x0043BBD0`: ниже порога `DAT_0060E040` берётся
«статическое» решение напрямую, выше — смешивается с решением, ограниченным по
скорости сходимости (клампы `DAT_0060E02C`/`DAT_0060E030`), что убирает
выбросы силы на малой скорости.

Продольное/поперечное складываются в «круг трения» через угол контакта
(`wheel+0x214` — предельный угол пятна, `0x220` — вес между моделями,
`0x224/0x228` — параметры сглаживания нагрузки, фильтр в `wheel+0x1F8`).

### 5.3a Состояние переноса силы шины **[КОД, ЗАМЕР]**

Коэффициенты уже есть в загрузчике и раскладываются по восстановленным слотам
1:1 — это проверено, а не предположено:

| сеттер скрипта | слот `wheel+0x1E8+i*4` | дефолт `Wheel.java` | поле у нас |
| --- | --- | --- | --- |
| `setSliction` | 0 (C0) | 1.4 | `TireParameters::sliction` |
| `setFriction` | 2 (C2) | 1.49 | `friction` |
| `setStiffness` | 4 (C4) | 15.2 | `stiffness` |
| `setMaxLoad` | 11 | 8000 | `maximum_load` |
| `setFrictn_x` | 12 | 1.0 | `longitudinal_grip` |
| `setLoadSmooth` | 14 | 0.4 | `load_smoothing` |

Остальные слоты `Tyre.java` пишет явными константами: `[1]=[3]=[5]=[6]=[7]=[9]=[10]=0`,
`[8]=-1`, а `[2]` — через `setFriction`. Разные компаунды меняют именно эти поля, поэтому
весь набор теперь едет в `TireParameters::pacejka[17]`.

Восстановлено и переносимо без домыслов:

- **Закон силы** — `0x0043BA80` (с зажимом `max(F,0)`) и `0x0043BB30` (знаковый), по слотам
  `C0…C10`; форма подтверждена дословно (§5.3).
- **Низкая скорость** — `0x0043BBD0` перенесён (§12.12).
- **Кривая нагрузки** — `min(0x214, load)` и `atan(load·(π/2)/0x214)·0x214·(2/π)`,
  смешанные весом `0x220`; `0x214` = `setMaxLoad`, `0x220` = `setLoadSmooth`
  (`0x00441190` и `0x004411D0` в таблице регистрации нативов `0x004427E0`).
- **Составное скольжение** — `sqrt(sin²α + (cosα·slip·0x218)²)`, где `0x218` = `setFrictn_x`
  (`0x00441050`).
- **Раздача** — поперечная сила это знаковый `0x0043BB30` БЕЗ множителей
  (строка `local_7c = (sinα/σ)·0x0043BB30(angle, s)` листинга), продольная —
  `0x0043BA80` с множителями `(slip·0x218·cosα/σ)`. Множитель `0x1F0` в прикладную
  силу НЕ входит: строка `wheel[0x158] = закон · wheel[0x1F0]` пишет grip-слот
  (0x00454500), а не прикладную силу. Это тот же класс ошибки, что и в сигма-баге
  (коэффициент/сила), он же был в строке 655 ниже и в §5.3c — исправлено 2026-11-24.

**Не восстановлено и поэтому НЕ перенесено:** масштаб аргумента `local_3C`. В листинге он
равен `((|v_patch|+1)·0.5) · load_term`, и при таком прочтении сила растёт линейно со
скоростью скольжения без предела, чего быть не может. Значит либо `b8/b4` — не скорости, либо
масштаб приходит из `susp+0x50` / `wheel+0x6C` (в `wheel[0x158]` поперечная сила умножается
именно на них). Пока это не выяснено, переносить формулу нельзя: пришлось бы выдумать
делитель, а это ровно то, что запрещено.

Следующий шаг — прочитать потребителя `wheel+0x158` и `susp+0x50`, чтобы получить масштаб,
и только потом заменить выдуманную кривую в `tire_model.cpp`.

### 5.3b Конвейер силы шины — точный листинг **[КОД]**

Прочитано из `0x00454500` дословно; здесь всё, что нужно для переноса.

**Вход.** На кадр берётся объект контакта `C = wheel_record+0x30`, и колесо `W = C+0x7c`.
Контакт есть, если `C[0x38] > C[0xd8]`; иначе скольжение обнуляется (`0x14C`, `0x150`, `0x158`).

**Скорости в пятне.** Вектор скорости в пятне переводится в систему колеса матрицей
`W+0xa4 + W[0x20c]·0xd4` (три компоненты): `v_roll = comp2`, `v_lat = wheel[0x140]`.
Поверхностная скорость `v_surf = −(wheel[0x60]·wheel[0xc0])`.

**Скольжение и угол.** `0x0043BBD0(v_surf, v_roll, v_lat, dt, &slip, &angle)` — §12.12.

**Составное скольжение.**
```
σ = sqrt(sin²α + (cosα · slip · frictn_x)²)          // 0x218
если σ ≤ 1e-4 -> запомнить slip/angle, сила 0, выход
```

**Кривая нагрузки** (зажим `max_load` = `0x214`, вес `load_smooth` = `0x220`):
```
load_term = (1-load_smooth)·min(max_load, load)
          + load_smooth · atan(load·(π/2)/max_load) · max_load · (2/π)
```

**Масштаб аргумента — решён.**
```
ŝ      = M · (C[0xac], C[0xb0], C[0xb4])    // вектор контакта в системе колеса
s      = ((sqrt(ŝ[1]² + ŝ[2]²) + 1) · 0.5) · load_term
```
Это **не скорость** (проверено: `C[0xac]/0xb0/0xb4` — точка/нормаль контакта, а не
скорость пятна) и берутся именно **две касательные компоненты**, без компоненты 0. У
колеса, стоящего нормально к дороге, проекция нормали на касательные оси ≈ 0, поэтому
`sqrt(...) ≈ 0` и `s ≈ 0.5 · load_term` — то есть сцепление выходит

```
F_lat ≈ C2 · 0.5 · load · sin(C0·atan(...)) · wheel[0x1F0]
     ≈ 1.49 · 0.5 · load · 0.8 · 1.5  ≈  0.9 · load        (μ ≈ 0.9)
```
Ровно тот порядок, что нужен. Единица внутри `(x+1)/2` — не случайная: это пол, благодаря
которому шина держит даже когда нормаль точно совпала с осью; наклон контакта (крен,
кембер) добавляет сверху до удвоения. Отсюда видно и место нашего выдуманного
`alignment = max(.25, tilt²)`: в оригинале эта роль распределена так — нормаль даёт
множитель масштаба, а кривая нагрузки — прогрессивность по нагрузке.

**Что именно лежит в `C[0xac..b4]` — решено.** Это **нормаль контакта**, а не точка.
Доказательство от противного по коду: вектор читается **только поворотной матрицей**
колеса (`pfVar10[0]·x + pfVar10[4]·y + pfVar10[8]·z`, столбцы матрицы с шагом 0x10 по
`0x0042f660`), без переноса. Мировая точка контакта под такой матрицей дала бы компоненты
порядка мировых координат (сотни-тысячи), и `s` вышел бы абсурдным. Единичный вектор —
единственное, что даёт `s` порядка нагрузки.

Отсюда и роль развала: наклон нормали в системе колеса меняет `sqrt(ŝ[1]²+ŝ[2]²)`, а с ним
и сцепление. Именно эту величину наша выдуманная `alignment = max(.25, tilt²)` и
изображала. Компонента 0 (ось, исключённая из проекции) — скорее всего ось качения
колеса или его ось поворота; при прямо стоящем колесе это не важно, но при развале
даёт разницу до двух раз, поэтому проверяется первым же замером бокового ускорения.

**Закон силы** — `0x0043BA80` (`F = max(F,0)`) и `0x0043BB30` (знаковый), по слотам:
```
m   = s·C1 + C2 ;  den = m·C0 ;  e = exp(−s·C5)
arg = (s·C9 + C10 + a) · ((s·C3 + C4)·e / den)      // a = σ или угол
q1  = atan(arg)
q2  = atan((s·C7 + s²·C6 + C8)·(q1 − arg) + q1)
F   = m · s · sin(C0 · q2)
```
Со слотами из `Wheel.java` (`C8=-1`, остальные нули) это сводится к
`F = C2·s·sin(C0·atan(a·C4/(C2·C0)))`.

**Распределение.**
```
F_long = (slip · frictn_x · cosα / σ) · 0x0043BA80(σ, s)
F_lat  =  (sinα / σ) · 0x0043BB30(angle, s)      -- без множителей (исправлено)
сопротивление качению = s · v_roll · wheel[0x21c] · 0.01 − F_long
wheel[0x158] = 0x0043BB30(angle, s) · wheel[0x1F0]   -- grip-слот, НЕ прикладная сила
wheel[0x1F0] = поверхность[0x50] · wheel[0x6C]       -- поверхность · износ (боковой)
```
`wheel[0x158]` — хранимый grip-коэффициент для косметических потребителей:
его читает снапшот колеса в рендере частиц дыма (`FUN_005226a0` копирует
0x14C/0x150/0x154/0x158, зовёт пакет частиц `FUN_005248c0`); в прикладные силы
он не входит, потребители в покрытии декомпа на этом заканчиваются.

**Шаг колеса.** `Δω = dt · 50 · wheel[0xec] · F_long · wheel[0x60] · 2.8`
(`DAT_0060E020 = 2.8`), затем кламп статика/скольжение:
```
если знак(slip_new) == знак(slip_old)   — принять Δω
иначе                                   — домножить на |slip_old / (slip_new − slip_old)|
wheel[0xc0] += Δω ;  wheel[0x148] += Δω · wheel[0x60]
```

**Что переносить НЕ надо:** фильтр `0x1F8` (мёртв), `0x224/0x228` (не пишутся).

### 5.5 Раздача момента и скорость вала — точный код **[КОД]**

Скорость вала (`car+0x1E14`) — **средневзвешенное по `drive`**, а не среднее
арифметическое (`0x00454500`, строки 561–578):

```
car[0x1E14] = 0; sum = 0
для каждого колеса, у которого ЕСТЬ тело (wheel+0x30 != 0)
                    и drive > 0.001 и |wheel[0xC4]| > 0.001:
    car[0x1E14] = (sum · car[0x1E14] + (−wheel[0xC0] · wheel[0xC4]) · drive) / (sum + |drive|)
    sum = |drive| + sum
```

Это точное средневзвешенное `Σ(−ω·0xC4·drive) / Σ|drive|`. Фильтр — **наличие
тела**, а не контакт: поднятое колесо с `drive > 0` участвует.

Применение момента (`строки 686–736`):

```
local_40 = car[0x1E14] · total_ratio                 // скорость до сцепления
... двухинерционная связь (§4) ...
Δshaft   = (local_40/total_ratio − shaft_prev) / Σ|drive|
на колесо:  wheel[0xC0] += −(Δshaft · drive) / wheel[0xC4]
```

Важно:

- в `wheel+0xC0` добавляется **готовый шаг угловой скорости** (рад/с), не сила
  и не момент;
- **делителя-инерции здесь нет** и **`dt` нет** — момент/инерция уже свёрнуты в `Δshaft`;
- на это приращение **нет клапа** — ограничение работает только в следующем
  проходе (клап `≤ 1` в дифференциале) и в шине через силу;
- `wheel+0x60` (метры) — радиус для пятна контакта и плеча импульса;
  `wheel+0xC4` — отдельный делитель того же смысла. Ни один native его не
  пишет — значение приходит из конфигурации объекта колеса.

Если `wheel+0xC4 == 1`, арифметика размерно сходится: `0xC0` — рад/с,
`car[0x1E14]` — рад/с, а шина считает `r·ω` в м/с через `0x60`. Поэтому при
переносе это поле проще всего считать единицей и проверить на живой игре.

## 7. Тормоза

`Brake` **[СКРИПТ]**: `friction`, `radius`, `force`, `torque = force·friction·radius`;
у деталей также `friction_pad`, `friction_disc`, `number_of_calipers`, `diam_mm`.
`Chassis.brake_balance` (0.5) — распределение осей, `brake_balance_can_be_set`.

Native **[КОД]**: `setBrake`/`setHBrake` пишут номинальные значения в `wheel+0xD0`
и `+0xD4`, а действующие (`+0xD8`, `+0xDC`) пересчитываются с учётом износа диска
(`wheel+0x164`) по тому же закону `1 − w²·0.6`. Тормозной момент в шаге:

```
M_brake = physics[0x37] · handbrake · wheel[0xDC]        // ручник, ось 2
        + (wheel[0xFC] + brake) · physics[0x36] · wheel[0xD8]  // рабочий тормоз
        + wheel[0xF0]                                     // добавка от износа
если M_brake > 0:
    Δω = dt · 50 · wheel.relax · M_brake · const
    колесо подтягивается к нулю не более чем на Δω (без перелёта через 0)
```

то есть `physics[0x36]`/`[0x37]` — баланс тормозов по осям (`brake_balance`),
а `wheel+0xFC` — вклад конкретной детали `Brake`.
Износ тормозов: `wheel[0x188] += (M_brake − wheel[0xF0]) · 10 · |ω| · dt · 50 · 0.001`,
и при `wheel[0x164] ≥ 1` тормоз отключается: `wheel[0xF0] += 100`,
эффективность `×0.2`, искры.

## 8. Аэродинамика

`Chassis.fully_stripped_drag = 0.333`, у моделей — 0.53…0.61;
`C_drag` считает скрипт: `C_drag = max(0, fully_stripped_drag − Σ drag_reduction)`
(`Chassis.updatevariables`). Native читает `drag_center` (Vector3) и `C_drag`
в `0x00448430` и кладёт в `physics+0x23F…0x242`. Крылья (`Wing`) задают
`wing_F` (прижимная сила) и `wing_dir` — они попадают в `physics+0x908` (сила)
и `physics+0x8FC` (точка приложения).

Прижимная сила считается в шаге **[КОД]** как квадратичная по скорости и
прикладывается в точке крыла:

```
v_acr = скорость тела в точке крыла
F     = −|v|² · wing_F
импульс = F · dt, приложенный в physics+0x8FC
```

Там же гасится энергия превышения (ограничение импульса по `max`), то есть
крыло не может «выстрелить» машину при большом dt.

## 14. Таблица момента: точные формулы из бинарника

Восстановлено по декомпиляции `0x004b7020` (шаг цикла, момент считается в конце
цикла), `0x004b77f0` (свип, пишет таблицу) и `0x004b69a0` (геометрия).
Листинги: `E:/OpenSLR/rea/ghidra_out/decomp/`.

Геометрия (`0x004b69a0`), поля банка в байтовых смещениях:

```
bore        = 2*piston            (+0x5c)      stroke   = 2*crank (+0x60)
area        = piston^2 * pi       (+0x68)
swept       = area * stroke       (+0x6c)      Vmax     = swept + Vmin (+0x70)
Vmin        (+0x10)               compression = Vmax/Vmin (+0x74)
speed_limit = 45.0                maxRPM = (45/crank)*9.549296 (+0x8c)
смещение за шаг = d_angle*crank    (+0x170)
```

Расчёт цикла (конец цикла, `0x004b7020`):

```
MEP        = work / (Vmax - Vmin)                              // +0x184
torque     = (Vmax - Vmin) * MEP * cylinders * 0.125           // +0x188 → таблица 1
gross_power= (rpm/60) * (Vmax - Vmin) * MEP * cylinders        // +0x190
friction   = rpm^3 * 2e-8                                      // в ВАТТАХ
net_power  = gross_power - friction                            // +0x194 → таблица 2
horsepower = net_power * 0.001341                              // +0x18c
```

**Три вещи, которые нельзя прочитать иначе:**

1. В момент идёт множитель **0.125**, а не `1/(4π)`. Это 1.5708× — то есть таблица
   оригинала на 57 % щедрее «физически правильной» формулы. Порт обязан брать 0.125.
2. **Трение в момент не вычитается.** `0x188` — это индикаторный (gross) момент,
   и именно он идёт в таблицу. Трение `rpm³·2e-8` — величина в ваттах, и снимается
   только с мощности (`0x190 → 0x194`).
3. Мощность считается как `rpm/60 · работа`, без деления на два для четырёхтактного
   цикла, поэтому hp в игре вдвое выше «физического» при том же моменте. Это
   соглашение оригинала, а не ошибка чтения: обе формулы видны рядом.

Свип (`0x004b77f0`): `rpm = i·step`, `period = 1/(rpm·0.008333334)`,
`angular = rpm·0.10471976`, `piston_speed = angular·crank`,
`dt = period·0.0043290043`, затем `prepare()`, `reset_cycle()`, итерации
сходимости (10 повторов, полоса 5 %, `prev = mean·0.6 + prev·0.4`), в таблицы
пишутся `+0x188` (момент) и `+0x194` (мощность).

`prepare()` (`0x004b6bf0`) и шаг цикла (`0x004b7020`) в порте уже совпадали с
оригиналом построчно — расходились только эти три строки.

### 14.7 `wheel[0xEC]` и `gearbox+0xE8` — снято живьём, формула подтверждена **[ЖИВОЙ ЗАМЕР]**

Снято `rea/live_e8.ps1` (PID 83872, MC, машина в мире, 1-я передача, сцепление
выжато, машина катится назад на `ω ≈ −8.37` рад/с).

```

clutch_openness [1DBC] = 1.000        throttle = 0.000   brake = 0.000

wheel[2..3] (задние,   share[e0]=1): ω=−7.8451   EC[ec]=0.00285528135 -> fVar16=35.0228195
```

Формула `0x00454500:446` даёт для заднего колеса

```

= (1/2)·(1−0.999608)·|2.666·3.230 = 8.61118|·13.5162 + 35

```

Выводы:

1. **`gearbox+0xE8` = инерционный член `fVar16`** — 35 у MC, ровно шестая
   величина записи двигателя (§5.3b). Не «мёртвое» поле и не масштаб тормоза.
2. **`wheel+0xEC` = `0.1/fVar16`**, то есть при `fVar16 = 35` это `2.857e-3`, а
   не `3.3e-2`, которого ждала гипотеза «`E8` огромен». Обратная величина
   (`1/EC = 350`) — **масштабированная**, не кг·м²: шаг колеса умножает её на
   свой коэффициент (см. п. 5), поэтому эффективная инерция колеса
   `J_eff = fVar16/(5·K)`: 1.0 кг·м² для шины и 1.17 для тормоза на нейтрали.
3. **Передние колёса получают ровно `E8`** (`share = 0` обнуляет приводной член),
   задние — `E8 + 0.02` при выжатом сцеплении. Включённое сцепление добавляет
   `0.5·8.61·13.52 ≈ 58`, то есть на 1-й передаче `fVar16 ≈ 93` (`EC ≈ 1.07e-3`) —
   колесо «тяжелеет» в 2.7 раза. Это и есть механизм, которого не было в порте
   (там фиксированный `wheel_inertia = 1.6`).
4. **Противоречие масштаба тормоза закрыто — оно было в чтении, а не в игре.**
   `C = педаль·1000·3270` (прежняя запись §5.3b) — ошибка: множителя `1000` в
   формуле нет, `wheel+0xD8` **уже** момент в Н·м (MC: перед 2284.423, зад
   3270.387, ручник 6540.775 = 2× зад). Настоящий отклик при `fVar16 = 35` —
   `2803·педаль` рад/с² (ниже, п. 5): на 100 % педали колесо с 94 рад/с встаёт за
   ~0.03 с, на 1 % — за ~3 с. Это прогрессивный тормоз, а не «блокировка при
   0.5 %».

5. **Оба коэффициента шага прочитаны по инструкциям** (не эвристика):

   ```
   0x455C5B  fld [ebp+0xc]      ; dt
   0x455C5E  fmul [0x5F0EEC]    ; 50
   0x455C66  fmul [esi+0xEC]    ; EC
   0x455C6C  fmul [ebp-8]       ; T (сумма моментов, см. ниже)
   0x455C6F  fmul [0x60E024]    ; K_brake = 4.0 в файле, 6.0 в памяти
   ```
   ```
   0x4563B6  fld [ebp+0xc]      ; dt
   0x4563B9  fmul [0x5F0EEC]    ; 50
   0x4563BF  fmul [esi+0xEC]    ; EC
   0x4563C5  fmul [ebp-0x18]    ; F_long
   0x4563C8  fmul [esi+0x60]    ; радиус колеса
   0x4563CB  fmul [0x60E020]    ; K_tyre = 2.8 в файле, 7.0 в памяти
   ```

   `T` (0x455C12..0x455C47) собирается так:

   ```
   T = (pedal_brake + wheel[0xFC]) * physics[0xD8] * wheel[0xD8]
     + pedal_handbrake * physics[0xDC] * wheel[0xDC]
     + wheel[0xF0]                       ; rollF, у MC = 20
   ```

   Отсюда и смысл живых `physics+0xD8/0xDC = 1.0/1.0` (§14.8): это **масштабы**
   перед скобкой, а момент берётся из колеса. Коэффициенты `K_brake = 6` и
   `K_tyre = 7` — это те самые `0x0060E024` и `0x0060E020` из §14.4 (в файле
   4.0 и 2.8), то есть мод правит `.data` при старте. Никаких «2.8/50·4»
   вперемешку: у шины и у тормоза **разные** `K`.

   Эффективная инерция при `EC = 0.1/fVar16`: `J_tyre = fVar16/(5·K_tyre) = 1.0`
   (на нейтрали), `J_brake = fVar16/(5·K_brake) = 1.17`. Прежняя константа порта
   `wheel_inertia = 1.6` — в 1.4–1.6 раза «тяжелее» замера, но того же порядка:
   масштаб был не в 1000 раз мимо.


### 14.7a Нейтраль и вторая машина: fallback подтверждён живьём **[ЖИВОЙ ЗАМЕР]**

Повторный замер на той же машине, стоящей **на нейтрали** (`gear=0`,
`car+0x1DBC = 0`, `shaft[1E14] = −0.1508`, педали 0). Изменилось ровно одно —
передаточный множитель стал нулём:

```
wheel[0..1] share=0  ω=0.1524/0.1459  EC[ec]=0.00285714283 -> fVar16=35
wheel[2..3] share=1  ω=0.1715/0.1512  EC[ec]=0.00285714283 -> fVar16=35
```

Задние колёса ушли с `35.0228195` (1-я передача) на **ровно 35** — тот же самый
бит-в-бит результат, что у передних. Это закрывает третью ветку fallback
(`total_ratio == 0`) уже на **приводных** колёсах: при нулевом отношении
приводной член выключен целиком, добавки нет. В передаче он был всего `0.0228`
при выжатом сцеплении, и именно это не давало различить «`E8` — весь
знаменатель» и «`E8` плюс малый член».

В том же проходе зонд поймал **вторую машину** (трафик, AWD с дробными долями):

```
J_engine[E0]=20  J_drive[E4]=1000  J_8[E8]=50  rearend[40]=2.11
car: gear=0  clutch[1DBC]=0  shaft=0.0002  idle=83.78 (800 rpm)  maxRPM=7000
wheel[0..1] share=0.1 ω=∓0.0012  EC=0.00200000009 -> fVar16=50
wheel[2..3] share=2   ω=∓0.0009  EC=0.00200000009 -> fVar16=50
```

Три вывода:

1. **`E8` действительно инерция конкретного двигателя** (35 на MC, 50 здесь,
   по другим машинам 38/40): четыре колеса одной машины дают одно число.
2. **Доли привода не влияют на fallback** — у этой машины они `0.1/0.1/2/2`, а не
   `0/0/1/1`, и всё равно ровно `E8`. Значит ветка проверяет `sum|share|`,
   `share` и отношение, но не их величину.
3. **`wheel[0xEC]` хранится как `float32`**: `0.1/50` в double — ровно `0.002`, а в
   памяти `0.00200000009` (ближайший float). Для порта это несущественно
   (9-я значащая цифра), но объясняет, почему замер не совпадает с double
   в последних разрядах.
### 14.7b Порт переведён на `EC` — что сдвинулось **[КОД + ЗАМЕР]**

Модель колеса в `src/physics/vehicle_dynamics.cpp` больше не использует
`wheel_inertia = 1.6` в отклике на шину и на тормоз: оба шага берут `EC` из
§14.7 (per-wheel, с fallback), а `wheel[0xE0]`-доли, сцепление и отношение
приходят из `DriveInput` (`brake_inertia` = `gearbox+0xE8`, `tyre_step_gain` =
`[0x0060E020]`, `brake_step_gain` = `[0x0060E024]`, `wheel_clutch_open_` =
`car+0x1DBC`). `wheel_inertia` остался только в сцеплении и дифференциале — это
собственная модель порта, не этот листинг. `brake_scale`/`handbrake_scale`
удалены: абсолютные cfg-величины `brake_power`/`handbrake_power` момент больше не
масштабируют (§14.8), но их **отношение** и есть момент ручника (§14.7c).

Строки (120 Гц, те же фикстуры, до → после):

| строка | `1.6` | `EC` |
|---|---|---|
| 0–100 км/ч | 4.41 с | **4.02 с** |
| максималка | 227 км/ч | 224.5 км/ч |
| тормозной путь (grip 1.0 / 1.25) | 32.28 / 28.07 м | 31.86 / 28.08 м |
| букс 3 с, 470 Нм, только передние тормоза | срыв > 5 м/с | 3.69 м/с, `F/Fz = 1.55` |
| слайд: минимум оборотов | 6912 | **1687** (порог теста 1600) |
| слайд: самое медленное приводное колесо | 0.0 рад/с | 0.1 рад/с |

Три вывода, которые важнее самих чисел:

1. **Пин в фикстуре не сдвинулся** (0.1 рад/с против 0.0). Инерция самого
   колеса причиной пина не была — и не могла быть: она масштабирует отклик, а
   не баланс моментов. DRV-7 остаётся открытым.
2. **Обороты в слайде просели с 6912 до 1687** при пороге теста 1600 — то
   самое «колесо встало, а с ним и обороты», на что жаловался водитель. Водитель
   проверил живьём 2026-11-15: **обороты в слайде не глохнут**, поведение почти
   как в оригинале. Значит строка фикстуры пессимистична, а неверна по сути: в
   игре сцепление и газ держат двигатель, чего фикстура (нейтраль + сброс газа)
   не воспроизводит. Порог 1600 не трогаем, но и не считаем его приговором.
3. Букс стал на 3.7 м/с вместо > 5 при той же насыщенной шине (`F/Fz = 1.55`):
   шина теперь держит колесо в 1.5 раза сильнее, и утверждение теста переписано
   с порога по проскальзыванию на проверку насыщения (`|F| > 1.4·Fz`), которое
   от калибровки инерции не зависит.

`test_vehicle_dynamics` 36/36, `test_drive_faithful` 18/18, `test_missing_support`
16/16. `test_physics_tick_rate` даёт 6/9 — **те же три строки красные и на HEAD**
(проверено откладыванием правок в stash и пересборкой): это не регрессия
переноса, а отдельный долг по лимитеру.
### 14.7c Ручник — это 2× задний тормоз и кнопка, а не педаль **[ЗАМЕР + КОД]**

Данные: в `_main_.cfg` каждой машины есть `brakepower <brake_power> <handbrake_power>`
(парсер — `part_config.cpp`, команда `brakepower`). У всех 27 рейсеров это
`1000 2000`, а у трафика встречается и `1000 700`, и `3200 2000`: отношение
задано данными, а не константой. Живой замер заднего колеса MC совпадает с ним
точно: `wheel+0xD8 = 3270.387`, `wheel+0xDC = 6540.775` — ручник ровно вдвое
сильнее стояночного, потому что игра строит оба момента из одного коэффициента.

Порт на этом месте ошибался дважды, и обе ошибки перемножались:

1. `out.handbrake = wheel.brake` — брался стояночный момент без отношения, то
   есть половина (3270 вместо 6540).
2. педаль `.3` из первого импорта без происхождения. Привязка кнопочная
   (`in.drive_handbrake = axis(48) > .5`), поэтому у игры педаль 0/1; `.3`
   давало 0.3·3270 ≈ 981 Н·м при пределе сцепления заднего колеса ≈ 1700 Н·м —
   то есть ручник физически не мог заблокировать колесо ни на одной скорости.
   Стенд этого не видел, потому что сам ставил педаль в 1.0 (отсюда 60 -> 0.6 км/ч
   в прошлой записи), а в игре ручник оставался мёртвым — ровно как сообщал водитель.

Сейчас `out.handbrake = задний brake · handbrake_power/brake_power` (2× у всех
рейсеров, 0.625 у FireEngine по его данным), педаль 1.0. Тест
`the_handbrake_locks_the_rears_and_holds_far_beyond_the_pedal_hack`: 66 -> 43 км/ч
за 1 с, задние колёса 0.00 рад/с, передние 38.8 рад/с — блокируются ровно задние.

**Под газом.** Ручник — это момент, а не отдельный режим, поэтому он сравнивается
с моментом привода на колесе: `педаль · phys[0xDC] · wheel[0xDC]` против
`T_двигателя · i / 2` на заднее колесо. Пока тормозной момент больше, колесо
блокируется, а привод тянет двигатель вниз (в замере он садится к 1490 об). У MC
это `0.5·T·12.9 > 6540`, то есть мотор сильнее ≈1010 Н·м в первой передаче ручник
не удержит — так же ведёт себя и оригинал, потому что закон один.

**Сила ручника как настройка.** Два места, один и тот же закон: панель Ctrl+F12 ->
Tuning -> Driving и строка `HANDBRAKE STRENGTH` на странице GAME OPTIONS
(`java.game.OptionsDialog`, натив `getHandbrakeStrength()F` /
`setHandbrakeStrength(F)V`). Диапазон 0…5 шагом 0.1, **по умолчанию 1.4**; значение
пишется в `save/game/openslrr_options` (`handbrake=`), а не в `java.util.Config`:
у стокового Config фиксированный бинарный layout, и `player_handbrake` в
`save/game/options` не переживает перезапуск. Строку меню рисует класс из
`openslrr/patch` — это декомпилированный стоковый диалог плюс одна строка
(`HANDBRAKE STRENGTH`), то есть вёрстка в игре родная. Порт ставит этот каталог впереди классов установки
(`find_patch_root` + `Jvm::prefer_patch_root`), а сама установка остаётся
стоковой. В установку этот класс класть **нельзя**: он зовёт нативы, которые
есть только у порта, и оригинальный `StreetLegal_Redline.exe` падает на нём с
`native implementation missing for ...getRendererOption`. Исходник лежит рядом с
классом: порт пересобирает исходник, который новее своего класса, — и при
старте (движковые деревья), и при загрузке класса (любое дерево, включая
модовые `parts/<мод>/scripts`); оригинал делает то же самое при загрузке.
Множитель применяется к **моменту**
(`wheel+0xDC`), а не к педали: оригинальная кнопка остаётся кнопкой, 1 —
восстановленный закон без изменений, 0 отключает ручник целиком (включая
статическое удержание на месте). 1.4 — вкус водителя, а не замер: это значение,
на котором у переднеприводной машины задние колёса блокируются уверенно. Тест
`the_handbrake_strength_scales_the_recovered_moment` (газ удерживается, 40 км/ч):
сила 0/1/2 -> задние 51.8 / 33.1 / 0.0 рад/с через 0.5 с, 75 / 9 / 5 км/ч через 1 с.
### 14.8 Поправка к §5.3b: `gearbox+0xD8/0xDC` — НЕ `brakepower` **[ЖИВОЙ ЗАМЕР]**

Живые значения у всех 56 найденных объектов-физики: `+0xD8 = 1.0`, `+0xDC = 1.0`
(и `+0xD0/+0xD4 = 1.0` у настоящих машин). Ни у одной машины там нет 1000/2000.
Значит пара `+0xD8/+0xDC` — не cfg-параметр `brakepower`, а что-то вроде
множителя/флага (значение 1.0), тогда как момент тормоза приходит в
`wheel+0xD8/0xDC` другим путём (`setBrake`/`setHBrake`, `Brake.java`:
`момент·баланс`; у MC это 2284.423/3270.387 при 6540.775 ручника).
Перенос должен брать момент из колеса, а не масштабировать cfg-величину.

**Закон в коде и под тестом:** `wheel_slip_denominator` / `wheel_inverse_inertia`
(`include/slrr/vehicle_dynamics.hpp`, `src/physics/vehicle_dynamics.cpp`) считают
`fVar16` и `0.1/fVar16` дословно по листингу, включая per-wheel fallback при
`share ≤ 0.0001`. Тест `wheel_slip_denominator_reproduces_the_live_measurement`
(`tests/test_vehicle_dynamics.cpp`) прибивает к замеру: передние ровно 35.0000
(`EC = 2.85714283e-3`), задние 35.0228195 (`EC = 2.85528135e-3`), плюс все три
fallback-ветки. Смена модели колеса (`wheel_inertia = 1.6` → `EC`) — отдельный
проход: она двигает строки разгона/торможения и требует перебазирования.

**Методическая находка:** в гараже физика **не тикает** (`wheel[0xEC] = 0`,
`ω = 0`, `shaft = 0` у всех 56 объектов) — `0xEC` пишет только мировой шаг.
Зонд поэтому работает в режиме `-Watch`: он ищет машину, у которой `0xEC` уже
ненулевой, и только её считает измеренной. Из меню/гаража замер невозможен,
